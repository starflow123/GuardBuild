# 攻击方式构造与自学习闭环 · 执行方案

> 状态：2026-10-31 用户授权「按这份文档全部开始做」，未逐条挑的选项已取文档里标注的推荐值（见第七节）。
> 本文只定边界、交付项与验收。每完成一项里程碑，代码与本节状态同步更新。

## 一、这份方案解决什么问题

现在每新增一种攻击方式，都要在静态识别、攻击用例生成、判定证据、靶场、测试这五处各写一遍代码。
人工成本让能力扩展速度锁死在"一次一族"。同时，每次扫描失败的根因只留在一份不进仓库的临时报告里，
复盘全靠人坐下来看日志——同一形状的坑（挂载前缀重复、登录假成功、列表必须带分页参数）会在下一个框架上再犯。

本方案要装两条通道：

1. 让模型参与"想打法、写实现"，但**打法能说什么、结论怎么算**由写死的程序决定。
2. 让失败自动记账、按类别累积，使"这一步为什么没打中"变成可查询的数据而不是一次性对话。

## 二、两个环：不要混为一谈

| | 环 1 · 能力增长环（慢） | 环 2 · 找靶调优环（快） |
| --- | --- | --- |
| 学什么 | 新增一种打法 / 新增一个动作 | 同一种打法怎么找得更准 |
| 谁驱动 | 用户逐次批 | 可由用户手动触发自动跑 |
| 改动范围 | 新工具、新配方、新考卷 | 只动提示词、候选菜单构造、预算排序、抽取配方 |
| 主要风险 | 悄悄扩大"能碰什么" | 分数上涨但真实项目没变强 |
| 模型调用 | 本地/GUI；CI 与门禁模式禁用 | 本地/GUI；CI 与门禁模式禁用 |

两环只有两个交点：

- 失败账本里"测不了：动作表表达不了"这一类，是能力请求单的输入来源。
- 判卷器复用"不许回退"的复跑比较代码，所以判卷器必须等它。

## 三、术语拆名（同名概念三处易混）

| 名字 | 是什么 | 谁能改 |
| --- | --- | --- |
| 动作表 | 执行器（真正发请求的写死程序）能做的动作清单：用哪个身份、什么方法、打到哪、带哪些查询参数与请求体字段、塞什么载荷、要不要并发或先走一步、打完从哪几个通道回读 | 只随新工具注册而变长 |
| 配方 | 一张填好的表：这一族攻击具体怎么打、拿什么当证据 | 模型起草，判卷器验，用户批 |
| 判据 | 什么情况下算"打穿了"（例：归属人复读确认内容确实是他的对象） | **冻结**，自动环不许写 |
| 考卷 | 同一项目的三份变体：有漏洞版、加固版、干净对照版，各带已知答案 | 模型可起草，已知答案需用户过目 |
| 判卷器 | 拿考卷验配方的写死程序 | 冻结 |
| 失败账本 | 累积的、按五类分好的失败记录，附原始请求与响应摘录 | 程序自动写，人只读 |
| 能力请求 | "动作表表达不了，我需要新动作"的申请单 + 权限声明 | 模型提，用户批 |

## 五、里程碑与执行顺序

依赖关系决定真实顺序（不是编号顺序）：

```
M0  1 失败账本 → 2 不许回退                      （纯确定性，零模型，先立门）
M1  4 动作表 → 5 试点一族打通 → 5b 放量另两族 → 13 探索区
M2  6 判卷器 → 7 同源考卷防御 → 8 补齐+冻结 → 14 双提议 → 15 对比代理
M4  9 能力请求 → 10 审查代理 → 12 终审报告      （试点一族全新攻击族走完整链）
M3  3 提示词版本化 → 11 调优候选                （快环跑通一次真实调优）
M5  其余十族配方化 + 老实现成组退役
M6  16 经验库写出去 → 17 读进来
```

每个里程碑结束都要交：单测 + 相关 e2e 轮次 + 白盒/黑盒基准不回退 + 提交推送 + 本文档状态更新。

## 六、红线（写进实现，不做成开关）

1. 判据、考卷已知答案、退出码映射、写/删探测的默认开关、动作表本身——自动环物理上不许写。
2. 判定用的请求序列必须来自已注册配方，模型不许在判定环节自己发请求（否则无法重放）。
3. 对比代理与审查代理只能置"退回"，没有资格写"通过"状态字段。
4. 结论字段（漏洞 / 未复现 / 测不了）只能由判卷器落笔；模型可以写一份结论草稿供人读，草稿不改变状态。
5. 外部文本（网页、知识库、别人的报告）只能作为候选来源，进不了判定链。本仓库真实发生过一次工具返回内容夹带指令。
6. 凭据值不落：配置、凭据注入、事件流、report.json、report.md、证据库、磁盘缓存，再加失败账本、能力请求单、终审报告、经验库条目——共九条渠道零残留。
7. 被测对象只用自建靶场与公开项目。个人项目不进这个环，也不作为被攻击对象。落到产物上：`benchmarks/failure-ledger.jsonl` 与 `benchmarks/green-baseline.json` 是要进仓库的，因此这两份文件里一律不写个人项目——连项目名都不落，即使显式打开了个人层。
8. 新工具注册即默认关闭；CI 能不能用它单独再批一次。

## 七、已定决策（未逐条挑的取推荐值）

| 待拍项 | 决定 | 备注 |
| --- | --- | --- |
| 执行顺序 | 按第五节依赖序 | M1 先只打通一族，跑通再放量 |
| 加固版考卷来源 | 由漏洞版自动插一处补丁派生 | 禁止手写两份，防同源自洽 |
| 新工具默认状态 | 中间态：自建靶场自动跑，真实项目需显式打开 | 纯默认关会造出永不被验证的器官 |
| 冻结集切分时机 | 先补齐考卷再切（第 8 项内完成） | 有族只有一份考卷，一留就没 |
| 快环触发方式 | 手动，用户点 | 不挂无人值守的自动重试循环 |
| 试点族 | 越权读 → SQL 注入 → 敏感文件泄露 | 三者分别代表归属类 / 内容差分类 / 外部资源类，判据形状各不相同 |
| 老实现退役 | 列残留接口与引用清单，交用户选一次全删或保留一个版本周期 | 不默默留作归档 |
| 对比代理与审查代理 | 保持两个角色、各自独立提示词 | 合并会让多样性检查与权限检查互相污染 |
| 模型下结论 | 不采纳（用户 2026-10-31 明确放弃） | 状态字段仍由判卷器独占，模型只写结论草稿 |

## 八、我认为还会失败的地方（做的时候逐条验证）

1. **过拟合考卷**：调优能看到的考卷越多，越可能只在这些形状上涨分。冻结集是唯一防线，所以第 8 项不能跳。
2. **同源考卷**：模型既提配方又造考卷，最省事的做法是造一份"恰好满足自己"的考卷。第 7 项的补丁派生是针对这一条的，采纳后要实测它能不能被绕过。
3. **第 5 项动老代码**：等价改造最容易把"零误报 46/46"碰坏。所以一次只改一族，改完立刻跑全量基准，出问题能定位到单族。
4. **调优价值未证**：如果真实瓶颈是"框架根本不认识"（Java/Spring 那种静态候选为空），调提示词完全无效——因为候选清单是空的。失败账本攒够后先看"打不中"里有多少来自候选缺失，再决定快环投多少。
5. **经验库可能没人回读**：第 16 项写了一年如果没人查，说明跨项目经验复用的价值被我高估，第 17 项就到此为止。
